# M6-2 上行、回滾與衝突（伺服器端）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 伺服器模式把使用者在任何裝置上對投影檔 frontmatter 的修改寫回 CalDAV（標題、狀態、日期、清單），越界的修改回滾，刪除／改名投影檔會被還原，LiveSync 衝突由伺服器以程式解決，`_request` 指令生效；狀態回饋寫在 `_sync`／`_sync_msg`／`_conflict`。另先做 S9 實測，決定 §8.8（客戶端能否分辨 LiveSync 帶來的變更）。

**Architecture:** 三方比對。伺服器記住「上次寫出的投影」（`projections` store：每個投影檔的受管欄位與 body 快照）。檔案的值（mine）≠ 上次寫出（base）的可寫欄位 = 使用者修改，經 `planUpstream`（純函式）轉成 0.5.0 的 `PendingUpdate`／MOVE／DELETE，交給既有引擎送出（`If-Match`、412 自動合併、衝突狀態都沿用）。`planReconcile` 改成三方：有待送修改的檔案不覆寫使用者的值；待送失敗或衝突時投影 `_sync`。

**Tech Stack:** TypeScript、vitest + fake-indexeddb、spike 實例 + playwright-core + 兩個接專用 CouchDB 的 vault（沿用 `spike/m6-probe/`）。

**Spec:** `docs/plans/2026-11-23-m6-server-projection-design.md`（§3 P2、§6.2、§7.1、§8.2、§8.5–§8.8）；實測 S7、S8（`docs/plans/2026-11-23-m6-0-spike-results.md`）。

## Global Constraints

- 只動伺服器模式；客戶端（0.5.0 行為）不變。`mode` 預設 `"client"`。
- 伺服器對投影檔：既有檔只用 `processFrontMatter`；還原刪除的檔才整檔寫入（內容來自 `projections` 快照）。**body 只在還原時寫入，且必須等於快照。**
- 寫回 CalDAV 一律經既有 `PendingUpdate` 佇列與 `applyPatch` 逐行修補（§4.4 寫入保留）；新增的修補能力也必須逐行修補、保留未知欄位。
- 可寫性沿用 `src/ical/editable.ts`（重複 VTODO 狀態唯讀；重複 VEVENT、帶 override 全部唯讀；`_deleted: true` 全部唯讀）。
- 全天 VEVENT 的 `end` 是含當天（§6.2）：寫回時 DTEND = end + 1 天。
- 系統欄位：`aliases`、`_kind`、`_uid`、`_notes`、`_rrule`、`_etag`、`_hash`、`_sync`、`_sync_msg`、`_deleted`、`_conflict`；客戶端只可寫 `_request`。
- LiveSync 內部 API（S7）只在特徵檢查通過時使用；不通過 → Notice 一次、停用自動解衝突。
- 整合驗證只用 spike 實例、臨時 vault、臨時 CouchDB 資料庫 `m6-spike`、Radicale 臨時集合；結束清理並附驗證輸出。不碰 `markdowns`、正式 vault、正式實例、正式集合。
- 每個 Task 結束 `npm test` 全綠、`npm run build` 通過。

## Review Focus

1. **伺服器剛同步到新值、還沒重寫檔案時，有 `changed` 事件**：不得把舊值當成使用者修改送出 → Task 4 `base-not-cache`（三方比對以 `projections` 為 base，不以快取為 base）。
2. **使用者修改尚未送出時，伺服器又因原生客戶端的修改要重寫同一檔**：不得蓋掉使用者的值 → Task 5 `pending-keeps-mine`。
3. **伺服器自己的寫入、改名、`merge-into` 刪除**：不得被當成使用者動作而回寫或還原 → Task 6、Task 7 的 `own-write-noop`、`own-delete-not-restored`。
4. **重複 VTODO 的 `status` 被改**：不送出，值回滾，`_sync_msg` 說明 → Task 4 `recurring-status-rejected`、Task 9 e2e。
5. **`due_time` 打成 `9:5`、`25:00`、日期打成 `2026/11/24`**：拒絕並說明，不送出 → Task 4 `invalid-values`。

### Task 4: `planUpstream`（純函式）

**Files:** Create `src/projection/upstream.ts`；Test `tests/projection-upstream.test.ts`

**Interfaces:**
- Consumes: `ProjFm`、`WRITABLE_KEYS`、`listName`（M6-1）；`editable`（`src/ical/editable.ts`）；`Patch`
- Produces:
```ts
export type UpstreamResult =
  | { kind: "none" }
  | { kind: "body-only" }
  | { kind: "send"; patch: Patch; move?: string /* 目標集合 href */ }
  | { kind: "reject"; message: string }            // 不送出；伺服器以 base 的值回滾可寫欄位，寫 _sync rejected
  | { kind: "request"; request: "delete" | "dismiss-conflict" };
export function planUpstream(i: { mine: Record<string, unknown>; base: Record<string, unknown>; bodyChanged: boolean; obj: CalObject | undefined; collections: CollectionInfo[] }): { result: UpstreamResult; rollbackSystemKeys: string[] };
```
規則：
- 系統欄位（Global Constraints 列出者）mine≠base → 列入 `rollbackSystemKeys`（由呼叫端以 base 值寫回），不影響其他判斷。
- `_request` 為 `delete`／`dismiss-conflict` → `request`（其他值忽略並列入回滾）。
- `obj` 不存在或 base `_deleted: true` 且可寫欄位有變 → `reject("任務已刪除")`。
- 可寫欄位逐一比較（字串正規化）。VTODO：`title`→`summary`；`status`→`status`（小寫，只接受 `needs-action|in-process|completed|cancelled`）；`due`+`due_time`→`date`（兩者皆空 → `null`）。VEVENT：`title`；`start`+`start_time`→`date`；`end`+`end_time`→`end`（全天時加一天）。`list`→ 依 `listName` 找唯一的集合 href → `move`；找不到 → reject。
- 驗證：日期 `^\d{4}-\d{2}-\d{2}$` 且為真實日期；時間 `^\d{2}:\d{2}$` 且 00–23／00–59；有時間沒日期 → reject。
- 可寫性：依 `editable(obj)`；改了不可寫的欄位 → reject（訊息沿用 `applyPatch` 的中文訊息）。
- 只有 body 變 → `body-only`。

- [ ] **Step 1:** 失敗的測試（每項一個 test）：`title`、`status`、`status-invalid`、`due-date-only`、`due-with-time`、`due-cleared`、`event-start`、`event-end-all-day-plus-one`、`list-move`、`list-unknown`、`system-key-rollback`、`request-delete`、`request-dismiss`、`deleted-reject`、`recurring-status-rejected`（Review Focus 4）、`invalid-values`（Review Focus 5：`9:5`、`25:00`、`2026/11/24`、只有時間）、`body-only`、`none`、`base-not-cache`（Review Focus 1：obj 的值已經變了但 mine==base → `none`）
- [ ] **Step 2–4:** FAIL → 實作 → PASS；**Step 5:** Commit `feat(projection): upstream plan`

### Task 6: 伺服器上行管線

**Files:** Create `src/projection/upstreamRunner.ts`；Modify `src/projection/writer.ts`（每次寫入前先 `putProjection` 快照、記錄「自己的寫入」）、`src/main.ts`（server 模式掛事件）

**Interfaces:**
- Produces: `class UpstreamRunner { constructor(app, getSession, writer); start(): void /* 註冊 metadataCache changed、vault delete/rename */; }`；`ProjectionWriter.expect(path, op)`（自己的寫入、改名、刪除在 5 s 內被事件看到時忽略）

行為：
- `metadataCache.on("changed")`（`_caldav/` 內）→ 依檔案 debounce 1 s → 讀檔（`splitFrontmatter`）→ base = `getProjection(path)`；沒有 base（例如剛接手的檔案）→ 以目前內容建立 base，不送出 → `planUpstream`：
  - `none`：不動作；`body-only`：更新快照 body
  - `send`：以 0.5.0 `editObject` 同樣的方式合併進既有 `PendingUpdate`（同一物件一筆，`rev+1`），`move` 時呼叫新加的 `client.move(href, destHref)`（WebDAV MOVE，`Overwrite: F`）後更新快取；接著觸發同步
  - `reject`：以 base 的值寫回可寫欄位，`_sync: rejected`、`_sync_msg`
  - `request: delete` → `client.delete(href, etag)`（新增，`If-Match`）→ 成功後同步；`dismiss-conflict` → 移除該物件的 conflict 待送，清 `_conflict`、`_sync: ok`
  - `rollbackSystemKeys` → 以 base 值寫回這些鍵（同一次 `processFrontMatter`）
- 每次處理後更新快照（fm 取 mine 的可寫欄位＋伺服器寫回後的系統欄位，body 取 mine）

- [ ] **Step 1:** 實作（膠合程式；純邏輯由 Task 4、5 覆蓋）。`client.move`、`client.delete` 以 `tests/client.test.ts` 的 fakeTransport 加兩個 TDD 測試：`move sends MOVE with Destination and Overwrite F`、`delete sends If-Match`

### Task 7: 回滾與 LiveSync 衝突自動解決

**Files:** Create `src/projection/rollback.ts`、`src/projection/conflicts.ts`；Modify `upstreamRunner.ts`

行為：
- `vault.on("delete")`（`_caldav/` 內、非 `expect` 的自己刪除）→ 依快照整檔還原（frontmatter 以最新投影、body 以快照）；`vault.on("rename")` 從 `_caldav/` 改名或搬出（非自己的）→ `renameFile` 改回。快照不存在 → 只記 console，不猜內容。
- 衝突：每輪對帳後與每次 `changed` 時，對 `_caldav/` 檔案呼叫 S7 的呼叫序列：`getDBEntry(path,{conflicts:true})` 有 `_conflicts` → 兩版各自 `splitFrontmatter` → 最終內容 = 伺服器投影的 frontmatter（受管欄位以 CalDAV 為準）＋ `_conflict`（兩版可寫欄位中與伺服器值不同者，`{ 欄位: { mine: 裝置版的值, theirs: 伺服器值 } }`）＋ body（兩版相同取其一；不同則兩者以 `\n\n---\n（LiveSync 衝突合併）\n\n` 串接）→ `storeContent` → `resolveByDeletingRevision`。特徵檢查（四個方法都是 function）失敗 → Notice 一次並停用。
